# Capa 3.1 — comprobación de espacio libre en carpetas Temp

**Fecha:** 7 de noviembre de 2026. **Rama experimental:** `fix/partfile-safety-2026-11-04`.

## Problema confirmado por inspección del código

En `CDownloadQueue::CheckDiskspace()` se consulta `GetFreeDiskSpaceX()` para **cada archivo** cuando hay más de una carpeta `Temp` configurada, incluso si miles de `.part` residen en una única carpeta del SSD USB. Esta comprobación puede ejecutarse periódicamente y también a petición de otras operaciones. No hay todavía medidas reales de latencia ni de CPU en el equipo del usuario.

## Cambio

- Se consulta `GetFreeDiskSpaceX()` **una vez por ruta real `CPartFile::GetTmpPath()` dentro de cada comprobación**. Se conserva el resultado como `uint64` en un `std::map<CString, uint64>` local.
- Las rutas son las de los archivos `.part`, no letras de unidad: se evita mezclar volúmenes montados, rutas UNC, uniones y carpetas que podrían apuntar a destinos distintos. La comparación de claves es exacta; si difiere la escritura de la ruta se hará una consulta extra, opción conservadora.
- Si solo hay una carpeta `Temp`, se conserva la consulta única que ya existía antes.
- Si la comprobación de espacio libre está desactivada, no se consulta el disco.
- La señal `bNotEnoughSpaceLeft` sigue imponiendo **cero bytes disponibles** (sin usar ninguna caché). No se suavizan las pausas por falta de espacio.
- La caché **se destruye al terminar `CheckDiskspace()`**. La siguiente ejecución vuelve a consultar el disco: no se retienen valores entre llamadas, incluso si se conecta o desconecta una unidad USB.
- No se cambian ni las decisiones de `PauseFile(true)`/`ResumeFileInsufficient()`, ni los umbrales, ni las políticas de `FlushBuffer`/`FlushFileBuffers`, ni el formato de `.part`/`.part.met`.

## Efecto esperado (sin prometer cifras)

Con 10.000 archivos repartidos entre 3 rutas Temp distintas, la sección multi-Temp puede pasar de hasta 10.000 consultas de espacio libre por barrido a como máximo 3 consultas si todos los archivos pertenecen a esas rutas; no se afirma un porcentaje de aceleración ni una reducción de accesos físicos a disco medida. El coste de comparar rutas y mantener el mapa sigue existiendo.

## Validación

`scripts/test_io_layer3_contract.py` realiza pruebas estáticas de código y comparación determinista de decisiones con el algoritmo anterior para 0, 1, 15, 1.000 y 10.000 entradas; incluye carpetas múltiples, rutas UNC, archivos pausados o finalizados, señal de disco lleno y reconexión simulada de unidad USB. Se ejecuta en CI junto con las pruebas de las capas anteriores.

**Pendiente en Windows real antes de fusionar:**

1. Abrir el portable con una copia pequeña o un conjunto controlado de `.part.met` y tres carpetas temporales, sin abrir el eMule original al mismo tiempo.
2. Confirmar que las descargas se pausan o reanudan igual que antes, tanto con espacio suficiente como con espacio por debajo del umbral.
3. Desconectar y reconectar una unidad **solo cuando ambas aplicaciones estén cerradas**, comprobar detección de rutas ausentes y reinicio correcto. No forzar la desconexión de un disco mientras se escriben `.part`: el riesgo de corrupción es real.
4. Medir consultas de sistema de archivos y consumo de CPU con 1, 1.000 y más de 10.000 descargas; comparar con la compilación anterior bajo condiciones equivalentes.
5. Verificar que se conservan rutas personalizadas de «Descargar en…», categorías y progreso tras cerrar y volver a abrir.

**Puerta de seguridad:** no fusionar a `main` ni afirmar ganancias cuantitativas sin las pruebas funcionales.
